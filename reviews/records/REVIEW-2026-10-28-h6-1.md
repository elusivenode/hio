## Findings

### F-REVIEW-2026-10-28-h6-1-1 — high, open: an unsupported `accepted` row can be received

`tools/hio_receive.py:423-425` treats any occurrence of `accepted` anywhere in an imported record as support for `accepted` in an added index row. `_check_record_row` (`:274-309`) checks a new Assigned reviews row's id, base, head and assignment source, but does not check its status or scope. In a disposable Git fixture I added a review record whose verdict was `READY` and whose body said **“Nothing was accepted or approved.”** I added an Assigned reviews row for that record with status `**accepted**` and an unrelated scope. The receiver's dry run passed all checks. With `--publish` against the disposable bare origin, it returned 0 and imported the false `accepted` row into remote `main`. The reviewer record contained no owner acceptance. This violates §6.2 step 5.6's refusal of unsupported `accepted` and the rule that acceptance is a separate owner action. The index validator must bind row fields and state to the correct authority, not to a word occurring in prose. Add a negative test with a negated acceptance statement and a new accepted row, including the published receipt path.

### F-REVIEW-2026-10-28-h6-1-2 — high, open: a negated verification outcome can close a finding

`tools/hio_receive.py:390-391` decides that a verification record states a finding's outcome when the finding id and state word occur anywhere on the same line. A direct call to `check_index` with an imported `VERIFY-R-1` record containing **“F-OLD-1 remains open; do not mark verified_closed.”** and an existing finding row changed from `open` to `verified_closed` returned an empty problems list. The row cited that verification record; its other cells were unchanged. This is a false Class S transition under §6.2 step 5.6: the record explicitly says the finding remains open. Require a structured, affirmative outcome tied to the finding id and test a negated and a merely quoted state word. This finding is separate from F-1 because it can falsely close an existing finding even if new Assigned reviews rows are prohibited.

### F-REVIEW-2026-10-28-h6-1-3 — medium, open: a second assignment for the same target is accepted

`tools/hio_assign.py:193-205` refuses the same head only if the new scope wording differs. In a disposable index containing an active assignment at the exact H6 head, I invoked `hio_assign.py --apply` with a new review id, the same repository, base, head and scope. It exited 0 and inserted the second assignment. Harness-0.9 proposal §6.1 says this tool **“refuses a second assignment for the same target”**; §6.2 step 1 also requires one reconciled owner source when channels conflict. The same-scope exception creates two active review identities for one target. Refuse another active assignment for the same repository and head regardless of scope, or obtain an explicit owner change to the H6 design before activation. Add a CLI test with the same target and scope.

### F-REVIEW-2026-10-28-h6-1-4 — medium, open: valid transitions for later findings are rejected

The real `reviews/README.md` on `main` has a blank line after the S1a finding rows, before the ADR-0012 and T-0009 finding rows. `parse_tables` (`tools/hio_receive.py:178-197`) treats each contiguous run of pipe lines as a new table. The later finding rows form a run without a header, so `row_index` classifies none of them as findings. I took `main`'s actual index and changed the existing `F-REVIEW-2026-10-25-adr0012-1` row to `verified_closed`, preserving its id, review, severity, claim and waiver cells, citing an imported `VERIFY-X-1` record that states that finding's closure at the reviewed head. `check_index` rejected both the old and new lines as outside Class S, before it could assess the record. This prevents a valid §6.2 step 5.6 transition for current findings. Parse the findings section across its blank separator or normalize the approved index with an owner-authorised change, then test a Class S transition against the real index shape.

## Verdict and limits

The passing suite and nine planned failure cases show that the tested paths work, not that these index and assignment semantics hold. I did not approve H6, amend §6.2, activate either tool, accept work, waive a finding, or verify a remediation. Owner disposition is pending.
