## Findings

### F-REVIEW-2026-10-29-t0014-1-1 — high, open: rebuild can pass against a different release than the pinned one

`tools/restore_exercise.py:129-158` records the stored hash from `pins["releases"]` but reads the manifest and payload at `release.prefix`, which is built from the **rebuilt** hash. It never requires `release.content_sha256 == pins["releases"][ds]`. In a local probe, the store held two valid releases of `cash.aud.overnight`; the cutoff pin was `460b577b…b938`, the rebuilt release was `13e6f68b…1498`, and `compare_rebuild` returned `identical: true`. A store can legitimately hold several releases for a dataset. This makes a wrong-cutoff or wrong-input rebuild appear byte-identical to the pinned release. Compare against the pinned path and hash, and add a regression case with two stored releases for one dataset.

### F-REVIEW-2026-10-29-t0014-1-2 — medium, open: rebuild success does not require the running code and lockfile pin

`tools/restore_exercise.py:176-193` defaults `running_code_ref` to `None` and sets `ok` when the comparison is identical and `matches is not False`; `None` therefore passes. The CLI's `--check-running-code` is optional (`:269`, `:289-290`). The test at `tests/test_t0014_recovery.py:429-435` explicitly accepts exit 0 with `running_code_matches_pin: null`, while the same rebuild exits 1 when the flag detects a different running code reference. The P-3 acceptance criterion requires a rebuild from pinned code and lockfile. Make the pin check mandatory for a successful rebuild, and test that an absent or mismatched running reference cannot yield `ok: true`.
