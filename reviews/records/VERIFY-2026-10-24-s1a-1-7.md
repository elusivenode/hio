## Material counterexample: a revert falsely marked redundant

`VintageStore._verify_outcome` in `src/hio/marketdata/vintages.py` checks a
`redundant` row against **any** earlier equal-value vintage with sufficiently strong,
early evidence. It does not require the latest capture-order vintage to have the same
value, although `_redundant` at ingest does. Approved Q-002 OBS-INV-019 requires stored
vintages to equal the capture-order derivation of E(Q), and OBS-INV-018 requires pinned
recomputation to reproduce the result.

Reproduce in two disposable `LocalObjectStore`s with the same synthetic source
`synthetic.daily_source`, series `synthetic.rate`, valid date `2026-01-12`, and three
separately captured receipts, all ingested in `SCHEDULED` mode when honest:

| Capture at UTC | Value | `published_at` UTC |
|---|---:|---|
| 2026-01-12 01:00 | 3.60 | 2026-01-12 00:00 |
| 2026-01-13 01:00 | 3.61 | 2026-01-13 00:00 |
| 2026-01-14 01:00 | 3.60 | 2026-01-14 00:00 |

Process the first two normally in both stores. In the first store, leave the third
receipt unprocessed, then write a `catalogue/processed/` outcome for it with the correct
receipt id, source, capture time, `capture_mode=scheduled`, and its correct row identity,
value, derived `knowable_at` and `publisher_timestamp` basis, but falsely set
`disposition=redundant` and `vintage_seq=null`. The outcome's key is the normal
`catalogue/processed/<source>/20260114-010000000000-<receipt_id>.json`. In the second
store, ingest the third receipt honestly. Reopen both stores before querying
`as_known_by_market(synthetic.rate, T=2026-01-15T00:00Z,
Q=2026-01-15T00:00Z)`.

The forged store **serves 3.61** from two vintages; the honest store **serves 3.60** from
three vintages. Both views report the identical evidence digest
`e07ecbc446d96ff88403e57cf2942723a0feebff0507b3d2d1efe87cf6f3f1f6`.
An attempt to ingest the third receipt in the forged store then raises
`IncompleteProcessing: receipt ... is already processed`. The submitted forged-outcome
test changes a `vintage` row to `redundant` for a stronger-evidence duplicate; it misses
this revert, where an older equal value exists but the latest value differs.

**Smallest correction:** verify each outcome against the same capture-order ingest rule
used to create it. In particular, a redundant row must satisfy `_redundant`'s latest-value
condition against the correct prefix of earlier rows, as well as its evidence condition.
Reject a false no-op before query or resolution. Add this three-receipt fixture and
assert refusal of the forged state and byte-identical replay of the honest state, including
the digest. Preserve the approved contract and existing financial outputs. This is a
technical F7 correction within OD-0030/OD-0031, not a policy question.
