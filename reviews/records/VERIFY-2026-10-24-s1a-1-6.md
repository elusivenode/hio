## Independent findings

### 1. Q-002 completeness accepts an unprocessed receipt that changes the result

`VintageStore._check_processed` (`src/hio/marketdata/vintages.py`) calls a captured row a
no-op when its value equals the latest earlier vintage's value. It does not check whether
processing that row would add a vintage with stronger timing evidence. This contradicts
approved Q-002 OBS-INV-019: at Q, stored vintages must equal the capture-order derivation
of the captured evidence, or the query and resolution must refuse.

Reproduction, using only synthetic source `synthetic.daily_source` and series
`synthetic.rate` in a disposable `LocalObjectStore`:

1. Capture `2026-01-12,3.60,` at `2026-01-13T12:00Z` and ingest in `BACKFILL` mode. It
   adds a `schedule_only` vintage.
2. Capture the **same value and valid date**, this time with
   `published_at=2026-01-12T00:00:00Z`, at `2026-01-14T12:00Z`. Leave this receipt
   unprocessed.
3. Call `as_known_by_market(synthetic.rate, T=2026-01-13T00:00Z,
   Q=2026-01-15T00:00Z)`. It returns an empty value map instead of raising
   `IncompleteProcessing`. The evidence digest is
   `4be5beb5ad61f5a8aa8e83f3ff2703c43e3eb612a376e7a0f8a494c4a1785145`.
4. Ingest the second receipt in `SCHEDULED` mode. It adds a `publisher_timestamp`
   vintage for `3.60`. Repeat the identical `(T,Q)` query: it now returns
   `{2026-01-12: 3.60}` with the **same evidence digest**.

Thus a served result changes at fixed cutoffs while its pin does not. The author's
response acknowledges that capture mode is not recorded and treats this case as a no-op;
that admission does not satisfy the approved completeness rule. Smallest correction:
make processing/no-op disposition verifiable per receipt, including the evidence and
capture mode needed to derive whether ingest would add a vintage. Refuse the query and
resolution whenever that derivation cannot be established. Avoid using value equality
alone as the proof of a no-op. Keep receipt processing in capture order.

### 2. Q-001 inadmissible Q>T inputs reach a point-in-time release path

Approved Q-001 §4 says `as_known_by_market(T,Q)` with Q>T has
`predictive_pit_admissible=false` and must not feed any release labelled point-in-time.
`View` correctly computes the false flag, and `require_predictive_pit` rejects the view
when called. `build_releases` (`src/hio/jobs/s1a.py`) never calls that guard; it accepts
the mode as point-in-time and publishes from those views.

Reproduction: in a disposable synthetic S1a world, call `tests.test_pipeline.run` with
`mode=AS_KNOWN_BY_MARKET`, `cutoff=2026-01-12T00:00Z`, and
`quality_as_of=2026-01-29T00:00Z`. The call succeeds and publishes all four releases.
The released manifest names `knowledge_mode=as_known_by_market` while its view input
records `predictive_pit_admissible=false`. The guard's isolated unit test passes, but no
release-path test exercises it. Smallest correction: enforce predictive admissibility at
the point-in-time release boundary, before any release is published. If descriptive
Q>T output is needed, it must have a separately enforced descriptive designation under
the already approved Q-001 rule; no caller override is permitted.
