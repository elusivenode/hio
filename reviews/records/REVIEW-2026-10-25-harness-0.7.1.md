# Independent review: harness-0.7.1 revision 2

## Scope and method

The owner assigned this exact base, head, branch and subject by direct instruction, with a push-only exception for this review. `git ls-remote origin refs/heads/docs/harness-0.7.1-review-receipt` returned `9878dd0bad6fa61a0ef8519a6d47da7198b08526`; it descends from the assigned base. I cut an isolated worktree at the head and reviewed only the proposed package against approved harness-0.7 §6.2, `tools/check_review_branch.sh`, `tools/check_review_assignment.py`, OD-0050's actual PR #5 receipt and the stopped harness-0.8 proposal at `b86f497`. The package and its draft assignment are proposed, not authority.

I traced each receipt operation and challenged it with missing or changed records, false hashes, extra index rows, a moving remote branch, conflicting assignments, an interrupted tag push and a receiver who authored the reviewed work. No implementation or workflow file was edited.

## Seven assigned areas

1. **Reviewer provenance and byte-identical import.** M4 can prove imported file bytes equal files in an exact reviewer commit, provided the receiver uses the pinned commit and compares the staged Git blob ids (`docs/decisions/harness-0.7.1-proposal.md:121-153`). I independently checked the PR #5 precedent: `main@6fbec1a:reviews/records/REVIEW-2026-10-25-adr0012.md` and reviewer commit `1a05d8e:...` both have blob `f3f104da15295b3d6bfb3fe2cbb082cf481354bc`; tag `reviews/REVIEW-2026-10-25-adr0012` resolves to `1a05d8e`. The reviewer commit is not an ancestor of `main`. A matching blob proves content identity, not who operated the Git account or whether every adverse file was received.
2. **Assignment and scope.** The current scope script checks each commit from assigned head to review tip, forbidding non-review files, record rewrites and merge commits (`tools/check_review_branch.sh:23-75`). The assignment checker compares id/base/head/branch and assignment text with values supplied by the caller (`tools/check_review_assignment.py:50-93`). It cannot authenticate the caller-supplied assignment. Removing the reviewer PR also removes the independently triggered `pull_request_target` CI scope run (`docs/decisions/harness-0.7.1-proposal.md:112-119`); Claude or the owner must actually run the trusted `main` copy. Findings 1 and 2 address the remaining risks.
3. **Unapproved ancestry.** A receipt branch cut from `main` that imports only named `reviews/` files does not make the review commit, or its unapproved author ancestry, an ancestor of `main` (`docs/decisions/harness-0.7.1-proposal.md:37-67,130-150`). The scope script examines each reviewer commit, so an intermediate non-review edit reverted later still fails. This answers the central harness-0.8 objection without changing accepted S1a tools. The claim holds only if the receiver follows the import path; a direct merge is outside the procedure.
4. **Author as receiver.** Blob equality catches substitution of a different record *when the comparison runs*. It cannot force an author-receiver to import an adverse record at all. The procedure delegates routine receipt to Claude with no owner approval (`docs/decisions/harness-0.7.1-proposal.md:83-97`) and then calls the safeguards “mechanical, not trust” (`:160-167`). With no reviewer PR, a silent omission has no automated receipt trigger. Finding 1 requires this procedural dependency to be explicit and auditable; it does not call for a new authentication system.
5. **Adversarial cases.** The table below separates what the written procedure detects from what it assumes.

   | Case | Result under the proposal |
   |---|---|
   | Imported record changed after reviewer commit; forged `Record: ... sha256` trailer | Actual staged blob comparison to pinned T catches changed bytes if performed; a trailer alone proves nothing (`:137-147`). |
   | Reviewer branch missing every new record, or modifying a submitted record | `check_review_branch.sh` fails (`tools/check_review_branch.sh:19-22,45-69`). Omission of one of several expected records is not detectable without an independent expected-file list (finding 1). |
   | Add a second, false `verified_closed` index row without deleting the old row | Scope script permits `M reviews/README.md`; the import's “adds only lines” rule also passes. The meaning of the added row needs checking against the immutable verification record (finding 2). |
   | Reviewer branch force-pushed after the first `ls-remote` | The pinned commit T remains immutable, but step 5 never instructs a second remote-tip check before receipt; the stated stop condition is not executed (finding 3). |
   | Two conflicting owner-authored assignments | Approved §6.2 step 1 requires a stop (`docs/harness/operating-model.md:400-419`). The caller must discover both sources; the checker cannot do so from self-supplied text (finding 1). |

6. **Stop and recovery.** The listed mismatch conditions are suitable, but the text does not make all of them executable: `T=$(git ls-remote ...)` captures both SHA and ref, not a SHA, and there is no remote-tip recheck (`docs/decisions/harness-0.7.1-proposal.md:123-129,174-181`). More seriously, the tag is pushed *after* receipt is merged into `main` (`:149-153`). A tag-push failure produces a partial receipt with evidence already in `main` and no stated recovery (finding 4).
7. **Stopped harness-0.8 objections.** Stacked reviewer PRs and the accidental integration of unapproved ancestry are resolved by no reviewer PR and M4 import. Step 6's competing author PR is partly resolved: it directs remediation to the work's own branch, but retaining the first sentence of step 0 still needs its new `Submission-Head` kept current (`docs/decisions/harness-0.7.1-proposal.md:183-192`). Changing the descent checks and cutting reviewer branches from `main` are explicitly deferred (`:37-43`); the existing checks still work because the review branch starts at the assigned head. The old CI scope control becomes dormant and is replaced by a receiver-run check, a procedural loss, not an integrity improvement (`:112-119`).

## Findings

| ID | Severity | Finding and failure scenario | Required closure |
|---|---|---|---|
| **F-REVIEW-2026-10-25-harness-0.7.1-1** | **high** | **Assignment checking and adverse-evidence receipt depend on the author-receiver, but the proposal calls them mechanical safeguards.** The checker accepts whatever `--assignment-source` the receiver passes (`tools/check_review_assignment.py:84-92`). In the PR #5 precedent, OD-0050 says that value was taken from the record itself and the owner's exact image was unavailable (`docs/decisions/owner/OD-0050-receive-adr0012-review-evidence.md:50-63`). The package's step 5 also has no independent expectation of the number of reviewer files, and no reviewer PR or other automatic signal if Claude simply does not receive an adverse record. A forged matching assignment string, or silence after a push, can therefore be presented as a clean routine process if the owner does not compare the direct reviewer report. | Require the receiver to cite the actual owner-authored assignment source and the reviewer's independent tip and file-hash report, reconcile the complete file list, and report non-receipt or mismatch to the owner. State plainly that timely receipt and identity depend on procedural accountability. Do not use the record's own assignment field as the expected source. |
| **F-REVIEW-2026-10-25-harness-0.7.1-2** | **medium** | **Additive index edits can still assert an unauthorised disposition.** Step 5 accepts an `M reviews/README.md` patch if it only adds lines (`docs/decisions/harness-0.7.1-proposal.md:130-140`), while the scope script tests paths and file modes, not row semantics. Add a duplicate finding row saying `verified_closed` without removing the existing open row: the proposed additive and blob checks do not reject the false status. This contradicts the package's retained rule that only a Codex verification or owner waiver changes finding state (`:199-209`). | At receipt, compare every added index status or verification row with the immutable reviewer record and assigned scope; stop on duplicate IDs or unsupported closure. Keep routine navigation-only additions distinct from a finding-state decision. |
| **F-REVIEW-2026-10-25-harness-0.7.1-3** | **medium** | **The moving-tip stop condition is not implemented in the stated steps.** `git ls-remote` yields `<sha><tab><ref>`, so `T=$(...)` is not a usable commit id as written (`:125-127`). Even after parsing T and fetching, there is no second `ls-remote` before import completion. A force-push after the first check allows a receipt from a commit no longer at the submitted branch tip, contrary to `:174-175`. The content hash still pins that old commit; the defect is submission/assignment provenance. | Parse and validate exactly one 40-hex remote SHA; fetch that object; compare local and remote tips again immediately before committing/merging, stopping if either differs. State how to restart at a newly assigned head. |
| **F-REVIEW-2026-10-25-harness-0.7.1-4** | **medium** | **A tag-push failure can leave a completed merge with provenance preservation unfinished.** Step 5 merges the receipt into `main` before pushing the annotated tag (`:149-153`). If the tag push is rejected or the network fails, `main` contains the record while the tag promised to keep T reachable is absent. The generic “stop and report” instruction (`:123-124`) gives no way to complete or mark this partial state, and a later branch deletion can make the reviewer commit hard to recover. | Push and verify the immutable tag before the merge, or specify an idempotent recovery path that retries the exact tag at T and marks receipt incomplete until it succeeds. Never silently present a partial receipt as complete. |

## Verdict

**REQUEST CHANGES.** M4's byte-identical import and separation from unapproved author ancestry are sound, and the PR #5 precedent demonstrates them. The proposed procedure needs the four bounded corrections above before adoption. Blob ids and hashes establish content equality with a named commit; they do not authenticate a reviewer, discover conflicting owner instructions, guarantee that Claude receives adverse evidence, or prove a check was run. This review adopts no harness revision and changes no approved operating-model text.
