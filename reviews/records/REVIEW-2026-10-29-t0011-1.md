## Findings

### F-REVIEW-2026-10-29-t0011-1-1 — high, open: the alert queries a table the diagnostic setting does not select

`infra/tofu/monitoring.tf:14-33` sends blob logs to Log Analytics but omits `log_analytics_destination_type = "Dedicated"`. The same file's alert query at `:55-59` reads only `StorageBlobLogs`. Azure's default/null destination is Azure diagnostics mode, which writes to `AzureDiagnostics`; the resource-specific `StorageBlobLogs` table requires Dedicated mode. [Azure's resource-log documentation](https://learn.microsoft.com/en-us/azure/azure-monitor/logs/resource-logs) and the [AzureRM diagnostic-setting resource documentation](https://github.com/hashicorp/terraform-provider-azurerm/blob/main/website/docs/r/monitor_diagnostic_setting.html.markdown) state that distinction. The query's `union isfuzzy=true` with an empty datatable can discard a missing table and still return `WriteCount = 0` ([Kusto union documentation](https://learn.microsoft.com/kusto/query/union-operator)); thus successful attempt writes would not clear the missing-write alert. Set the destination to Dedicated or query the actual default table, and add a test binding the diagnostic destination to the alert's table. The adopted H4 S-9 audit log and T-0011 I-5 soak alert cannot be relied on at this head.

### F-REVIEW-2026-10-29-t0011-1-2 — medium, open: workflow failure notification has no configuration or evidence

T-0011 I-5 calls for a GitHub workflow-failure notification in addition to the missing-attempt alert. The assigned diff changes only `infra/tofu/` and tests. `infra/tofu/README.md:48-50` says the notification is configured in GitHub repository or account settings, but supplies neither a setting definition nor a recorded owner-side configuration or a concrete verification step. The Azure rule waits for a missing attempt over its default 26-hour window; it cannot establish immediate notification of a workflow that ran and failed. Record the GitHub notification setting and its owner-side verification or explicitly narrow I-5 with the owner. No GitHub setting change is inferred or requested by this finding.

### F-REVIEW-2026-10-29-t0011-1-3 — medium, open: the bootstrap output command ignores the external state file

The one-time runbook writes bootstrap state to `<STATE_DIR>/bootstrap.tfstate` through `plan -state` and `apply -state` (`infra/tofu/bootstrap/README.md:45-49`). Step 2 then runs `tofu -chdir=infra/tofu/bootstrap output` at `:53` without `-state`. OpenTofu's `output -help` says the omitted `-state` path defaults to the current directory's local state; that is deliberately absent here. The command therefore cannot return the backend values from the just-applied external state. Pass `-state=<STATE_DIR>/bootstrap.tfstate` to `output` and test the runbook's state path consistently through plan, apply and output.
