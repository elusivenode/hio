## Findings

### F-REVIEW-2026-10-25-t0009-1 — high, open: missing shared link can change the rights subject

`src/hio/publish/lineage.py:57-60` treats **every** receipt without a link as single-dataset, including F1 receipts captured under `rba.f1`. That makes `write_release` (`src/hio/publish/release.py:74`) check `rba.f1` instead of `rba.cash_rate`. I copied a valid synthetic store while removing every F1 link, then supplied a gate with `rba.f1` allowed and no `rba.cash_rate` record. `release_sources` returned `{'rba.f1'}` and `write_release` returned `True`. The existing test only supplies rights for the two dataset IDs, so it sees an incidental unknown-right denial. A missing link must refuse independent of the rights register's contents. Add a durable way to distinguish a shared-publication receipt and verify the expected link before attribution; test with the publication ID allowed and the actual dataset denied.

### F-REVIEW-2026-10-25-t0009-2 — high, open: substituted link can authorize an unrelated dataset

`rights_sources` checks that one link dataset contains the requested series, but does not check that dataset against the fixed series-to-dataset mapping or the built release's rights subjects (`src/hio/publish/lineage.py:65-78`). I copied the store with F1 links assigning `rba.cash_rate.aonia` to `wrong.dataset`; `release_sources` returned `{'wrong.dataset'}` and `write_release` succeeded with only `wrong.dataset` allowed. The vintage view would reject that swap if rebuilt, but publication takes a prebuilt release and does not re-run that view. Require a verified mapping at the publication boundary, and test a substituted single-owner link with the true dataset denied.

### F-REVIEW-2026-10-25-t0009-3 — medium, open: index comparisons silently omit periods

`src/hio/jobs/s1b1.py:243-250` builds levels only at period ends, so the first period's start is never in `levels`. The `continue` also silently drops later periods if either publisher endpoint is absent. On the synthetic fixture, AUD has 9 cash periods but 8 comparison rows; USD has 13 cash periods but 10 comparison rows. The release summary at lines 289-294 reports only compared rows, with no missing-period count or reason. It therefore cannot tell a reader which residuals were unavailable or unexplained. Anchor the base level at the first start, record every omitted pair and its cause, and independently validate the expected-bound model. `_decimals` at lines 150-157 uses the maximum precision visible after canonicalization, which is only a lower bound on the publisher's declared precision; it cannot by itself establish that a residual is solely publisher rounding.

### F-REVIEW-2026-10-25-t0009-4 — medium, open: S1b releases cite specs describing different inputs and calendars

T-0009 §2.6 includes the ADR gate (d) spec patches, but neither cash spec changed in this branch. `src/hio/jobs/s1b1.py:222-227,279` calls `spec_ref`, which returns the unchanged `0.2.0` versions. `specs/factors/cash.aud.overnight.yaml:24-33,38-45` still names `rba.cash_rate.overnight` from `rba_statistical_tables`, a Sydney calendar, and an undecided ex-ante/in-arrears regime; the actual release uses `rba.cash_rate.aonia` from `rba.cash_rate`, RITS selection and in-arrears accrual. The USD spec at `:17,25,37-40` likewise names the old source and calendar. A release with that `spec_ref` misstates its construction. Version the S1b contracts or give the outputs separate accurate spec references before submitting this slice as complete; preserve S1a outputs separately.

### F-REVIEW-2026-10-25-t0009-5 — medium, open: dated RITS and NSW reference inputs are absent

T-0009 §2.7 and acceptance A-8 require cited RITS/NSW reference data and a dated RITS fixture. `src/hio/jobs/s1b1.py:54-58` accepts externally supplied calendars; `tests/test_s1b1_releases.py:38-41` supplies a weekend-only RITS calendar and one hard-coded NSW holiday. There is no dated RITS/NSW fixture or loader/citation in this branch. The arithmetic with these synthetic calendars is correct, but it does not verify calendar selection against the intended reference data. Retain and cite dated reference fixtures, and test a date on which RITS and NSW differ, including the expected rate selection and period ends.

### F-REVIEW-2026-10-25-t0009-6 — high, open: successful attempts omit required key/value checks

HIO-ADR-0012 §4.3.3 requires each verified outcome to record `keys_checked` and a digest of each value; C3 later replays those digests against the held vintage. OD-0063 approves deferring the C1–C7 checks while writing records **in full**. `RunRecord.as_record()` (`src/hio/marketdata/runrecord.py:107-123`) has no `keys_checked`, and `run_capture.record_for()` (`src/hio/sources/run.py:104-120`) records a successful outcome after schema parsing and whole-body comparison without recording which keys or values it checked. The stored bytes permit a later parser to derive values, but they cannot reconstruct which keys this run claimed to check. Add the field and checks to the successful record, then test replay of an unchanged response and a response missing an expected key. This finding does not demand C1–C7 finality in this slice.

### F-REVIEW-2026-10-25-t0009-7 — medium, open: no due-time gate or scheduled workflow definition

T-0009 §2.5 calls for a scheduled capture workflow definition with cron slots and a local-time due check, disabled for live operation; §4 says the due local time is computed by that gate. No capture workflow exists under `.github/workflows/`, and no production caller of `run_capture` exists under `src/`. The function accepts `slot` and `slot_due_at` from its caller with defaults of `None` (`src/hio/sources/run.py:36-48`), then copies them into the record (`:104-120`). This cannot substantiate an intended-versus-actual slot or demonstrate the due check. Add the disabled definition and tested due-time computation, or explicitly narrow the authorised scope before accepting a record as complete. No live schedule should be enabled by remediation.
